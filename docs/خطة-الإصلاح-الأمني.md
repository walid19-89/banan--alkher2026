## 1. قواعد ثابتة لكل بند في هذه الخطة

1. **لا نشر إلى `main` قبل الاختبار على معاينة.** النشر إلى Netlify يدوي، وworkflows
   النشر إلى Pages/Worker وبناء APK أصبحت **يدوية** (`workflow_dispatch`) حتى لا
   يُنشأ إصدار أو نسخة ثانية عند أي push.
2. **نسخة احتياطية قبل أي لمس لقاعدة البيانات**، مع اختبار استعادة فعلي.
3. **ترتيب النشر الإلزامي:** قاعدة البيانات (متوافقة للخلف) ← الـ API ← الواجهة.
   السبب: الواجهة المخزّنة في PWA تتحدّث تلقائياً لدى المستخدمين (`autoUpdate` + `skipWaiting`)،
   فقد تعمل واجهة جديدة مع API قديم لدقائق — يجب أن يتحمّل الطرفان الفرق.
4. **لا تغيير في عقد الـ API** (المسارات، أسماء الحقول) في هذا التحديث. أي تغيير عقدي
   يحتاج إصدار APK جديد لأن النسخ المثبّتة (1.0.26/1.0.27) لا تتحدّث تلقائياً.
5. **نقطة رجوع جاهزة:** Netlify يحتفظ بسجل النشرات (Deploys → Rollback)، والوسم
   `v1.0.27` يبقى قابلاً لإعادة البناء.
6. بعد كل بند: تشغيل `npm run typecheck` + بناء إلى مجلد مؤقت (لا يلمس `dist`) ثم اختبار
   الدخول وإنشاء سند على معاينة Netlify بحساب واحد.

## 2. الأولوية P0 — يجب أن تُنجز في التحديث القادم

### P0‑1 إبطال الجلسات عبر `token_version`
- **المشكلة:** الرمز (JWT) صالح 30 يوماً، وبلا `jti` ولا عدّاد إصدار. تغيير كلمة المرور أو
  تعطيل حساب **لا يطرد** المستخدم، والجهاز المفقود يبقى داخلاً شهراً.
- **التغيير:**
  1. `ALTER TABLE public.fund_user_profiles ADD COLUMN IF NOT EXISTS token_version int NOT NULL DEFAULT 0;`
  2. إدراج `tv` في حمولة `signToken`، والتحقق `profile.token_version === payload.tv` داخل
     `requireUser`؛ اعتبر الرمز القديم بلا `tv` مساوياً لـ`0` (توافق للخلف — لا يخرج أحد فجأة).
  3. زيادة `token_version` في: تغيير كلمة المرور الذاتي، إعادة تعيين المدير، تعطيل الحساب،
     تغيير الدور. وتسجيل الحدث في `fund_audit_logs`.
- **الأثر:** الرابط لا يتغيّر · البناء يتغيّر (كود API فقط) · **قاعدة البيانات: عمود جديد فقط** ·
  المستخدمون: لا خروج جماعي إن طُبِّق التوافق للخلف؛ من غيّر كلمته سيُطلب منه الدخول مرة واحدة.
- **الترتيب:** SQL ← API. لا تنشر API قبل إضافة العمود (وإلا كل طلب يفشل).
- **الاختبار:** دخول، تغيير كلمة المرور، محاولة استخدام الرمز القديم ⇒ 401، والرمز الجديد يعمل.
- **الرجوع:** إعادة نشر الـ API السابق (العمود الإضافي لا يضرّ).

### P0‑2 إزالة رمز الجلسة من روابط الملفات
- **المشكلة:** `src/lib/api.ts → fileUrl()` يضيف `?token=<JWT>` لكل مرفق. الرمز يظهر في سجل
  المتصفح، سجل Netlify/CDN، وكيل الشبكة، وسجل أي مشاركة عبر واتساب (مسار مستخدم فعلي).
- **التغيير:** توقيع ملف قصير الأجل على الخادم (نمط `backupSignature` الموجود أصلاً):
  `HMAC(path + exp)` بصلاحية 10 دقائق، والتحقق منه في `/files/:name`.
- **توافق إلزامي:** **الاحتفاظ بقبول `?token=` (Bearer في الرابط) لمدة إصدارين على الأقل**،
  لأن APK المثبّت لا يتحدّث تلقائياً. بعدها يُحذف.
- **الأثر:** الرابط لا يتغيّر · البناء يتغيّر (API + الواجهة) · لا تغيير في قاعدة البيانات ·
  المستخدمون: لا شيء ملحوظ.
- **الاختبار:** فتح مرفق من الواجهة، ومِن APK قديم، ومن رابط منتهي (يجب 403).

### P0‑3 حدّ محاولات الدخول لكل حساب (لا لكل IP فقط)
- **المشكلة:** `rateLimit` يبني المفتاح على `x-forwarded-for` القادم من العميل ⇒ قابل للتجاوز
  بترويسة عشوائية. والأخطر أن فرض قفل صارم لكل IP يضرّ مستخدمي اليمن لأن كثيرين يشاركون
  **IP واحداً** عبر شبكات الجوال (CGNAT).
- **التغيير:** مفتاح `login:<email|phone>` (5 محاولات/15 دقيقة) + مفتاح IP واسع جداً
  (200/دقيقة) كخط ثانٍ + تأخير متدرّج + تسجيل المحاولات الفاشلة في سجل التدقيق.
  واعتماد IP المنصّة فقط (`context.ip`) مع تجاهل قيمة العميل.
- **الأثر:** الرابط لا يتغيّر · API فقط · لا DB (الجدول `fund_rate_limits` موجود) ·
  المستخدمون: **إيجابي** — لا حجب جماعي.
- **الاختبار:** 6 محاولات خاطئة لحساب واحد ⇒ 429 للحساب فقط، وحساب آخر من نفس الـIP يعمل.
- **ملاحظة:** لا تفعّل MFA في هذا التحديث (يحتاج واجهة ومسح QR وخطط دعم) — يُؤجَّل إلى P2.

### P0‑4 تقليل بيانات صفحة التحقق العامة
- **المشكلة:** `/public/verify/...` يعرض لغير المسجّلين **اسم المستفيد والمبلغ**؛ صورة سند على
  واتساب تكشف اسم متلقّي مساعدة ومبلغه.
- **التغيير:** إخفاء اسم الطرف أو تقنيمه (`أسرة أ. ع.`) مع إبقاء: رقم المستند، المبلغ، التاريخ،
  الحالة، والتوقيع. إظهار الاسم الكامل يصبح خياراً افتراضيه «مغلق» في الإعدادات.
- **الأثر:** الرابط لا يتغيّر · API فقط (شكل الاستجابة) · لا DB · المستخدمون: تغيير مرئي مقصود
  في صفحة التحقق فقط، والنسخ المطبوعة سابقاً تبقى صالحة.
- **الاختبار:** فحص QR لسند قديم وجديد.

## 3. الأولوية P1 — إن سمح وقت التحديث

### P1‑1 ترويسة `Content-Security-Policy`
- **المشكلة:** `netlify.toml` و`public/_headers` بلا CSP. (لا توجد اليوم ثغرة XSS: لا
  `dangerouslySetInnerHTML` في المشروع، وReact يهرّب النصوص، وتحقّق اسم الملف صارم.)
- **التغيير:** ابدأ بـ`Content-Security-Policy-Report-Only` لمدة أسبوع مع سياسة مقترحة:
  `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:;
  font-src 'self' data:; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'`.
  راجع تقارير المخالفة (الخطوط، Service Worker، صور الشعار) ثم فرّضها.
- **الأثر:** الرابط لا يتغيّر · لا بناء · لا DB · المستخدمون: **خطر كسر الأنماط/الصور إن أُسيء
  الضبط** ⇒ لا تُفرَض إلا بعد أسبوع تقارير نظيفة.

### P1‑2 تحصين رفع/عرض الملفات
- **المشكلة:** الـ API الحالي يتحقق من magic bytes ✅، لكن PDF يُعرض `inline` (سطح تصيّد)، ولا
  يوجد تنظيف للمرفقات اليتيمة.
- **التغيير:** `Content-Disposition: attachment` لـPDF أو عارض داخلي؛ مهمة دورية لحذف
  `fund_storage` غير المرتبط بأي سند/طلب؛ حدّ أقصى للمرفقات لكل مستخدم يومياً.
- **الأثر:** API فقط · لا DB (استعلام تنظيف) · المستخدمون: PDF قد يُنزَّل بدل الفتح المباشر.

### P1‑3 تشديد سياسة RLS لمشروع Supabase القديم
- **المشكلة:** `fund_events_read_authenticated … using (true)` تسمح لأي حساب بدور `member`
  بقراءة موجز كل الحركات المالية (نوعها، معرّفاتها، توقيتها).
- **التغيير:** قصر السياسة على الأدوار الداخلية، أو إخراج الجدول من `supabase_realtime`.
- **الأثر:** يخصّ المشروع القديم فقط (الـ API الحالي يستخدم `/sync`) · لا تأثير على Netlify ·
  النسخ القديمة من APK العاملة على Supabase تحتاج اختباراً قبل التطبيق.

### P1‑4 تقوية تطبيق أندرويد
- **المشكلة:** `android:allowBackup="true"` (سحب بيانات WebView بما فيها الرمز على الأجهزة
  الأقدم)، ولا `FLAG_SECURE` (تصوير الشاشات المالية)، ولا قفل عند العودة.
- **التغيير:** `allowBackup="false"`, `FLAG_SECURE`, وقفل PIN/بصمة اختياري.
- **الأثر:** لا رابط · لا بناء للويب · **يتطلب APK جديداً** · النسخ المثبّتة لا تتأثر.

## 4. الأولوية P2 — لاحقاً (لا تُنفَّذ الآن)

| البند | السبب في التأجيل |
|---|---|
| نقل الجلسة إلى كوكي `HttpOnly` | APK يعمل من `capacitor://localhost`؛ كوكي cross-site يحتاج `SameSite=None` وإعدادات CORS واختباراً على أجهزة حقيقية. الخطر أكبر من الفائدة الآن، وP0‑1 يغطّي أهم ثغرة. |
| MFA (TOTP) للمدير | يحتاج واجهة تسجيل الجهاز، رموز استرداد، ودعماً للمستخدمين. |
| تشفير النسخ الاحتياطية السحابية | يحتاج إدارة مفاتيح وتسلسل استعادة موثّق. |
| تعقيم/تحقق إدخال النصوص الحرة | دفاع عميق فقط (السلامة قائمة اليوم على React). |
| مراقبة/تنبيه على محاولات الدخول | يحتاج مزوّد تنبيهات. |

## 6. قائمة تحقق قبل كل نشر

- [ ] نسخة احتياطية جديدة + بصمة SHA‑256 محفوظة.
- [ ] `npm run typecheck` ينجح.
- [ ] بناء إلى مجلد مؤقت ينجح (`npx vite build --outDir <tmp>`) و`dist` الأصلي لم يُلمس.
- [ ] لا أسرار جديدة في الملفات المتعقَّبة (`git diff` مراجَع يدوياً).
- [ ] اختبار دخول: مدير، محاسب، عضو.
- [ ] اختبار إنشاء سند + مرفق + طباعة + تحقق QR.
- [ ] APK قديم واحد على الأقل يعمل (مرفق + دخول).
- [ ] خطة رجوع مكتوبة (رقم النشرة السابقة في Netlify).

## 7. تدوير الأسرار (مرتبط بهذه الخطة)

هذه البنود **لا تُطبَّق** إلا بإعلان مسبق لأنها تُخرج المستخدمين مرة واحدة:

1. تدوير كلمة مرور المدير (لأنها كانت مذكورة سابقاً في وثائق متعقَّبة).
2. تدوير `AUTH_SECRET` بعد نشر P0‑1 (يُبطل كل الجلسات — وهي النتيجة المطلوبة).
3. تدوير كلمة مرور قاعدة Neon، وتحديثها في متغيرات Netlify فقط.
4. نقل مفتاح الأرشيف المشفّر من `C:\Users\Elite\banan-archive-key.txt` إلى مدير كلمات
   مرور، ثم حذف الملف.
